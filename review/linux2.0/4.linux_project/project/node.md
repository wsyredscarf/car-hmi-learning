核心理解：
    环形缓冲区 + 互斥锁（线程安全）。
    termios 串口配置（8N1、非阻塞、原始模式）。
    Modbus RTU 状态机（逐字节解析）。
    epoll + 多线程架构（主线程监听，工作线程处理）。


面试官问：“你做过什么Linux项目？”
    答：
    “我基于Linux做过一个串口网关的原型。整体架构是主线程用 epoll 监听 TCP 和串口，三个工作线程分别负责串口读、网络读、串口写，用两个线程安全的环形缓冲区做数据中转，避免网络和串口速率不匹配导致丢数据。
    串口侧用 termios 配置成 8N1 原始模式，非阻塞打开，配合 epoll ET 模式；协议解析用的是状态机，处理 Modbus RTU 的粘包和半包，CRC16 校验通过才提交数据。
    这个项目让我对Linux的进程线程、文件IO、epoll、环形缓冲区、状态机、串口编程有了完整的实践。”

关键面试追问（准备这些）
    1.为什么用环形缓冲区而不是直接 read/write？
    “网络和串口速率不匹配，直接用会丢数据。环形缓冲区做速率适配，生产者写、消费者读，不阻塞。”

    2.串口用ET还是LT？为什么？
    “串口用LT更安全，因为串口数据量小，LT不会丢数据。网络用ET效率高，但必须配非阻塞循环读到 EAGAIN。”

    3.为什么串口读线程和epoll都要处理串口fd？
    “串口fd加入epoll是为了ET模式下及时响应，但真正读数据放在独立线程里，避免阻塞主循环。也可以只在epoll里读，看你架构设计。”

    4.如果客户端断了怎么办？
    “read 返回 0 表示客户端断开，关闭 fd 并从 epoll 删除，g_client_fd 置 -1，等待新连接。”

    5.环形缓冲区如果满了怎么办？
    “生产者停止写入，返回实际写入长度。如果频繁满，说明消费者太慢，考虑加大缓冲区或优化消费速度。”

    6.“你在Linux串口编程中遇到过什么坑？”
    “遇到过。在配置串口硬件流控时，CRTSCTS 宏是 GNU 扩展。如果在编译时用了严格的 -std=c99，这个宏就会被隐藏，报 未定义。我的解决办法是在 Makefile 里把编译标准改为 -std=gnu99，或者在源文件头部加上 #define _DEFAULT_SOURCE。这样既保留了 C99 特性，也启用了 GNU 扩展。这让我深刻理解了 C 语言标准库、GNU 扩展和编译器选项之间的关系。”
